# Claims Batch Processor — Reproducible Execution with Docker + Jenkins

A containerized batch job that consolidates **thousands of synthetic
insurance claims-extract CSVs** into a summary report — runnable
identically on a local machine or through a Jenkins pipeline. Built to
demonstrate Docker's **"reproducible execution"** pattern: a job that
starts, processes a batch, writes output, and exits, as opposed to a
long-running web service.

> **Data disclaimer:** every file used or generated by this project is
> synthetic and randomly generated (see `generate_sample_data.py`).
> Nothing here reads, stores, or references any real claims, policy,
> or policyholder data. This is a learning/portfolio project only, not
> connected to any production claims system.

## The scenario

Insurance claims processing is a genuinely good example of where this
pattern matters. Regional claims offices generate daily/nightly
extracts covering claim status, payout amounts, and volumes — at real
scale that's easily thousands of files across offices and lines of
business (auto, property, liability, workers comp). Platforms in this
space (for example, a commercial claims-management
platform) exist precisely to bring that kind of fragmented,
multi-system claims data together into one consolidated view — from
first notice of loss through payout.

This project models the **operational pattern** behind that kind of
consolidation step — not the platform itself, and not any of 
actual code, architecture, or data. It's a generic, safe-to-publish
illustration of "many extract files in, one consolidated report out,"
built the way a DevOps engineer would actually containerize and
automate that kind of job.

## Why Docker + Jenkins, specifically

- **Docker** solves *"does this run identically everywhere"* — every
  analyst's laptop, every environment, has the exact same Python
  version and dependencies baked in. No more "works on my machine."
- **Jenkins** solves *"does this run automatically, every time, without
  a human remembering to do it"* — same commands a person would type
  by hand, just triggered on a schedule or on every commit.

Both tools are running **the same underlying commands** either way —
that's the point of "reproducible execution": local testing and CI
aren't two different processes, just two different triggers for the
same one.

## What it does

1. Scans `/app/input` for all `.csv` claims-extract files (built for hundreds to thousands of files)
2. Per file: row/column counts, numeric column stats
3. **Aggregate rollup** across every file: total claims processed, total payout amount, payout broken down by claims office, claim counts broken down by status
4. Progress logged every 100 files (readable at scale)
5. A single malformed file is logged and skipped, not fatal to the whole run
6. Writes both JSON and plain-text reports, then exits

**Tested at scale:** 1,200 synthetic files (24,000 claim rows) processed in ~2 seconds, zero failures, correct office/status rollups verified.

## Project structure

```
.
├── Dockerfile
├── Jenkinsfile               # CI pipeline: build → test data → run → verify output
├── requirements.txt
├── generate_sample_data.py   # creates synthetic claims-extract files at any scale
├── app/
│   └── process_reports.py
├── input/                    # a few sample claims-extract CSVs ship here
└── output/                   # generated reports land here
```

## Run it locally

```bash
docker build -t claims-batch-processor .
docker run --rm \
  -v "$(pwd)/input:/app/input" \
  -v "$(pwd)/output:/app/output" \
  claims-batch-processor
cat output/summary_report.txt
```

PowerShell:
```powershell
docker run --rm `
  -v "${PWD}\input:/app/input" `
  -v "${PWD}\output:/app/output" `
  claims-batch-processor
```

## Test at real scale

```bash
pip install --break-system-packages -r requirements.txt
python generate_sample_data.py --count 2000 --rows-per-file 25
docker build -t claims-batch-processor .
docker run --rm \
  -v "$(pwd)/input:/app/input" \
  -v "$(pwd)/output:/app/output" \
  claims-batch-processor
```

Same command regardless of whether `input/` holds 3 files or 3,000 — that consistency is the whole point.

## Run it through Jenkins

1. Jenkins → New Item → Pipeline
2. Pipeline definition: "Pipeline script from SCM" → point at this repo → script path `Jenkinsfile`
3. Build Now

The `Jenkinsfile` does exactly what you'd do by hand: builds the image, generates a batch of synthetic test files, runs the container against them, and **fails the build** if `summary_report.json` wasn't produced — so a broken image can't silently pass CI.

## How this maps to real DevOps day-to-day work

If you're moving into a DevOps role, this project — small as it is — touches the actual daily responsibilities of the job, not just the tools:

| Day-to-day DevOps task | Where it shows up here |
|---|---|
| Writing/maintaining a Dockerfile | Layer ordering for cache efficiency, `.dockerignore`, no hardcoded entrypoint args |
| Writing a CI pipeline (Jenkinsfile) | Build → test → verify-output stages, with a failing build on bad output |
| Making pipelines environment-agnostic | Volume mounts instead of hardcoded paths; same run command locally and in CI |
| Handling failure gracefully at scale | Per-file try/except so one bad input doesn't take down a 1,000-file batch |
| Observability / log hygiene | Progress heartbeats every 100 files instead of unreadable per-line spam |
| Verifying a deploy/build actually worked | The Jenkinsfile's "Verify Output" stage — checking for the artifact, not just a zero exit code |
| Cleaning up after a run | `post { always { ... } }` removing CI-generated test data so the workspace stays reproducible |

In an interview, this project lets you talk concretely about *why* you made each decision (cache layer ordering, volume mounts, failure handling at scale) rather than reciting tool definitions — which is usually the actual difference employers are listening for in a career-switch candidate.
